# Отчёт по системному / End-to-End тестированию (Весенний этап)

## 1. Цель системного тестирования

Проверить продукт как целостную систему по бизнес-сценариям пользователя в рабочем окружении.

Ключевой бизнес-поток: «Пользователь регистрируется, авторизуется, выбирает фильм, работает со списком “Смотреть позже” и рейтингами».

## 2. Текущее состояние реализации E2E

### 2.1 Что реализовано
В проекте есть системный тест:
- `test/system/e2e_user_journey_test.go`.

Покрытые шаги:
1. Регистрация нового пользователя.
2. Логин и получение access token.
3. Просмотр профиля.
4. Получение списка фильмов.
5. Добавление фильма в watchlist.
6. Проверка watchlist.
7. Удаление из watchlist.
8. Создание рейтинга.
9. Проверка списка рейтингов.
10. Удаление рейтинга.
11. Проверка блокировки неавторизованного доступа.

### 2.2 Что настроено в CI
- Workflow: `.github/workflows/system-tests.yml`.
- Запуск: `push`, `pull_request`, `workflow_dispatch`, а также weekly `schedule`.

## 4. Рекомендация для полного соответствия UI-критерию

Чтобы преподаватель не придрался к формулировке про Selenium/Puppeteer и т.п., рекомендуется добавить минимум 1–2 UI E2E сценария, например на Playwright:

1. UI login (ввод email/password, проверка перехода в профиль).
2. Поиск фильма в UI + добавление в watchlist + проверка карточки в watchlist.

### Минимальный план внедрения UI E2E
1. Добавить `frontend` E2E тесты (Playwright).
2. Поднять `frontend + api + postgres` в CI job.
3. Запускать `npx playwright test` в `system-tests.yml` после backend E2E.
4. Сохранять screenshot/video/trace как artifacts.

## 7. Процедура расширения системных тестов

Пример расширения: добавление сценария «Изменение профиля пользователя».

1. Добавить шаги:
   - PATCH `/users/me` (смена email),
   - повторный GET `/users/me` и проверка обновления.
2. Добавить негативный шаг:
   - PATCH с невалидным payload → 400.
3. В UI-версии сценария:
   - заполнить форму профиля,
   - нажать Save,
   - проверить обновлённые данные в интерфейсе.
